# 示范：1. 两数之和 —— 一道题完整走一遍

> 这是给你第 1 周 D1 用的对照材料。做之前**不要先看**，做完再对照。
> 重点不是这道题的答案（这题太简单，答案网上一搜就有），而是**每一步在纸上写什么、花多少时间**。
> 作者：小算

---

## 题面

给定一个整数数组 `nums` 和一个整数目标值 `target`，请你在该数组中找出**和为目标值 `target` 的那两个整数**，并返回它们的数组下标。

- 假设每种输入只会对应一个答案
- 同一个元素在答案里不能重复出现
- 返回顺序任意

---

## 步骤 ① 读题（5 分钟，纸上写，不碰键盘）

在纸上抄下这四行——**这四行后来会成为你所有题的习惯**：

```
输入：nums（整数数组，长度 n），target（整数）
输出：两个下标 [i, j]，i != j
边界：n >= 2；值可能为负；可能有重复值
约束：恰好一个解，同一元素不能用两次
```

**这一步在干什么**：把自然语言翻译成「函数签名 + 约束条件」。很多 bug 不是算法错，是读题时漏了一个约束。

比如「同一元素不能重复出现」这句话，直接决定了后面代码里 `seen` 的写入时机——第 ④ 步会看到。

---

## 步骤 ② 想暴力解（7 分钟，纸上写，不碰键盘）

**先写能想到的最笨的解法。** 这一步的目的不是拿分，是**建立一个正确性基线**：我知道答案一定在这个范围里。

纸上的暴力解：

```
对每一对 (i, j)，i < j：
    如果 nums[i] + nums[j] == target：
        返回 [i, j]
```

手推一个小例子，`nums = [2, 7, 11, 15], target = 9`：

```
i=0, j=1: 2 + 7 = 9  → 命中，返回 [0, 1]
```

再推一个带重复值的，`nums = [3, 3], target = 6`：

```
i=0, j=1: 3 + 3 = 6  → 命中，返回 [0, 1]
```

两个例子都通。**暴力解是对的，但慢**：检查了 n(n-1)/2 对，时间复杂度 O(n²)，空间 O(1)。

**这一步的产出**：一个已知正确的答案 + 一个可比较的复杂度基线。

---

## 步骤 ③ 找瓶颈（8 分钟，纸上写，不碰键盘）

问自己一句话：**「哪里被重复计算了？」**

答案：对于每个 `i`，我都在从头到尾重新扫一遍数组找 `target - nums[i]`。**但我要找的那个数是固定的**——它就是 `target - nums[i]`，算一次就有了，不需要重新遍历。

所以瓶颈是：**「找某个数在不在数组里」这个动作被做了 n 次，每次 O(n)。**

优化方向就很清楚了：把「找数」这个动作从 O(n) 降到 O(1)。用什么？**哈希表。**

新的思路：

```
一边从左到右遍历，一边把"见过的数 → 它的下标"记到一个字典里。
对当前数 x，先问字典：我需要的那一半 target - x 见过没有？
    见过 → 那它的下标就在字典里，直接返回
    没见过 → 把 x 和它的下标记进字典，继续往后走
```

复杂度：每个元素只访问一次，字典查询 O(1) → 总时间 **O(n)**，空间 **O(n)**。

**这一步的产出**：一句话的瓶颈描述 + 优化后的算法描述。**写不出这两句，就别进入第 ④ 步。**

---

## 步骤 ④ 编码（15 分钟，一次写完）

```python
class Solution:
    def twoSum(self, nums: List[int], target: int) -> List[int]:
        seen = {}
        for i, x in enumerate(nums):
            need = target - x
            if need in seen:
                return [seen[need], i]
            seen[x] = i
        return []
```

**注意第 8 行和第 9 行的顺序**：先查 `seen`，再写 `seen`。这个顺序不是随手写的，是被题面那句「同一元素不能重复出现」**逼出来的**。

推演一下 `nums = [3, 3], target = 6`：

```
i=0, x=3: need=3, seen 是空的 → 没查到 → seen[3] = 0
i=1, x=3: need=3, seen 里有 3（下标 0）→ 返回 [0, 1] ✓
```

如果反过来写（先存后查）：

```
i=0, x=3: seen[3] = 0  ← 先把自己存进去了
          need=3, 查到 seen[3]=0 → 返回 [0, 0] ✗ 同一个元素用了两次！
```

**这就是「先想清原理再写代码」和「写完再调」的区别**：想清了，一次写对；没想清，写完发现 `[3,3], 6` 这个用例挂了，然后开始瞎改——把 `seen[x] = i` 挪上挪下，运气好改对，运气不好就一直错。

## 步骤 ⑤ 自测（5 分钟，跑 4 类用例）

不要只跑题目给的示例。按这四类各造一个：

| 类别 | 用例 | 预期 | 实际 |
|---|---|---|---|
| 题目示例 | `[2,7,11,15], 9` | `[0,1]` | ✓ |
| 重复值 | `[3,3], 6` | `[0,1]` | ✓ |
| 负数 | `[-3,4,3,90], 0` | `[0,2]`（-3 + 3 = 0） | ✓ |
| 答案在末尾 | `[1,2,3,4,5], 9` | `[3,4]` | ✓ |

手推负数那个：`i=0,x=-3 → need=3，seen 空 → seen[-3]=0`；`i=1,x=4 → need=-4，没有 → seen[4]=1`；`i=2,x=3 → need=-3，seen 里有，下标 0 → 返回 [0,2]` ✓

**四类都过，才算这题做完了。** 只过示例用例就提交，是新手最常见的自欺。

## 附：这题真正值得带走的三件事

**1. 「空间换时间」的第一次出现**

暴力解 O(n²) 时间、O(1) 空间；哈希解 O(n) 时间、O(n) 空间。这是你第一次见到「多花一点内存，把时间降一个数量级」——后面 100 题里这个交换会出现几十次。

**2. 「先查后存」是一种通用模式**

不是这道题的技巧。凡是「不能重复使用同一个元素」的题（比如 15 三数之和的去重、128 最长连续序列），都要检查「查询和写入的时机」。

**3. 这题在第 3 周还要重做一次**

D1 你只写暴力解就够了。第 3 周（哈希专题）回来重做时，要求 3 分钟内写出哈希解，并且能讲清「为什么先查后存」。**同一个题在不同阶段重做，是这个计划的核心机制，不是重复劳动。**

## 附：为什么「写完再搞懂原理」会翻车

假设你 D1 直接搜了题解，抄了这么一段：

```python
seen = {}
for i, x in enumerate(nums):
    seen[x] = i
    if target - x in seen:
        return [i, seen[target - x]]
```

跑一下题目示例 `[2,7,11,15], 9`：
- i=0: seen={2:0}, need=7, 不在 → 继续
- i=1: seen={2:0,7:1}, need=2, 在，seen[2]=0 → 返回 [1,0] ✓ 通过了！

**示例过了**。你会以为这题会了。

但提交时 `[3,3], 6` 直接挂：
- i=0: seen={3:0}, need=3, 在！seen[3]=0 → 返回 [0,0] ✗

而且返回值下标顺序也是反的。

**问题不在代码，在于「先存后查」这个顺序你没想明白为什么**。你只是抄了一个"看起来对"的形状。这种情况下你会在面试现场被一句「如果数组里有重复元素呢」问穿。

所以顺序只能是：**原理（能讲清）→ 代码（一次写对）→ 验证（找反例）→ 模板（提炼特征）**。
